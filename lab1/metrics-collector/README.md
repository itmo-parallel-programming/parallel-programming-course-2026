# Лаба 1: Коллектор метрик — реализация (Java)

Полное условие и итоговые таблицы — в [`../README.md`](../README.md).

**Стенд:** Apple M4, 10 ядер: 4 производительных + 6 энергоэффективных (`sysctl hw.perflevel0.physicalcpu hw.perflevel1.physicalcpu`), JDK 25.
Число потоков для замеров: **1, 2, 4, 8, 10** — 16 не берём, это больше числа ядер.

**Ограничения в коллекторах:** только `synchronized`, `volatile`, `AtomicLong`, `AtomicInteger`, `AtomicLongArray`, `ThreadLocal`, `ArrayList` под локом, `Thread.onSpinWait()`.
**Нельзя:** `ConcurrentHashMap`, `LongAdder`, `ReentrantLock` (на этапе 1), `AtomicReference` на массивы.

## Задачи

### Этап 0. База и замерялка
- [x] `Snapshot` и `MetricsCollector` по сигнатурам из условия.
- [x] Общие хелперы: корзина `min(value / 4, 255)`; перцентиль накопительной суммой до `count * q`, результат `index * 4`.
- [x] `SingleThreadCollector` без синхронизации.
- [x] `Zipf`: 2²⁰ значений из `[1..1023]` с вероятностью `∝ 1/k^1.15` и фиксированным seed. Массив генерируется **до** замеров. В корзину 0 попадает ≈35% (проверяется в `ZipfTest`).
- [x] `Benchmark`:
  - [x] у каждого потока свой локальный счётчик, без общих счётчиков;
  - [x] старт по `CountDownLatch`, остановка по `volatile boolean`;
  - [x] поток `k` начинает с индекса `k * 1000` и идёт по массиву по кругу;
  - [x] прогрев 5 с, потом 5 забегов по 5 с, берётся медиана;
  - [x] в конце печатается `snapshot().count`, чтобы JIT не выкинул код;
  - [x] **каждый коллектор запускается в отдельном процессе `java`**: имя коллектора передаётся аргументом.
- [x] Скрипт `run_all.sh`, который по очереди запускает все коллекторы и сохраняет результаты в CSV.
- [x] Замер baseline на 1 потоке.

### Этап 1. Один общий лок
- [x] `SynchronizedCollector`: `record` и `snapshot` под одним `synchronized`.
- [x] `EmptyLockCollector`: `record` только заходит в `synchronized` и сразу выходит.
- [x] Замерить оба варианта на 1/2/4/8/10 потоках.

### Этап 2. Шардирование локов
- [x] `StripedLockCollector`: 16 объектов-локов, корзина `b` защищена локом `b % 16`.
- [x] Сводка вне локов: `count`, `sum` через `AtomicLong`; `min`, `max` через цикл CAS (`compareAndSet`).
- [x] `snapshot()` по очереди берёт лок каждой группы и копирует её корзины, потом читает атомики.
- [x] Замер скорости.
- [x] `ConsistencyCheck`, общий для этапов 2–4:
  - [x] 4 пишущих потока, каждый сам считает свои вызовы `record()`;
  - [x] главный поток делает 10 000 `snapshot()` и проверяет `sum(buckets) == count`;
  - [x] выводит долю битых снимков и сколько раз было `sum < count` и `sum > count`;
  - [x] после `join` сравнивает итоговый `count` с суммой вызовов всех потоков.

### Этап 3. Thread-Local
- [x] `ThreadState`: `AtomicLongArray(256)` и `AtomicLong` для `count`, `sum`, `min = Long.MAX_VALUE`, `max = 0`.
- [x] Регистрация через `ThreadLocal.withInitial(...)`, состояние добавляется в `ArrayList` под локом.
- [x] `record()` без CAS: `setRelease(getPlain() + delta)`; `min`/`max` обычным сравнением.
- [x] `snapshot()`: скопировать список под локом, затем сложить корзины и сводки всех потоков.
- [x] Замер скорости и стресс-тест: почти 100% битых снимков.
- [x] P- и E-ядра M4 и почему рост скорости замедляется — см. ответы в [`../README.md`](../README.md).

### Этап 4. Двойная буферизация
- [x] `ThreadBuffers`: `long[2][256]` корзин, `long[2]` для `count`/`sum`/`min`/`max` (обычные поля, **не атомики**) и `AtomicInteger inside = -1`.
- [x] Глобальный `volatile int active` и `snapLock`. Регистрация нового потока идёт под тем же `snapLock`.
- [x] `record()`, рукопожатие Деккера (`DoubleBufferCollector.enter`).
- [x] `snapshot()` под `snapLock`: переключить `active`, дождаться ухода писателей, слить буфер в накопленный итог, обнулить (`min = Long.MAX_VALUE`, `max = 0`), посчитать p50/p99.
- [x] Стресс-тест: 0% битых снимков, итоговый `count` точно равен числу вызовов.
- [x] Эксперимент без шага 3 — отдельная реализация `NoRecheckDoubleBufferCollector` (`double-buffer-no-recheck`), чтобы не трогать рабочий код.
- [x] Замер скорости.

## Заметки
- M4 — это ARM, а не x86. Утверждения из условия вроде «seq_cst-чтения на x86 бесплатны» и «нет префикса `lock`» здесь работают по-другому, поэтому соотношения скоростей этапов 3 и 4 отличаются от ожидаемых.
- Замеры запускать без лишней нагрузки на машину, с подключённой зарядкой.
