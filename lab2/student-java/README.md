# Лаба 2 — коротко и по делу

**Запуск Java теперь настраивается переменными в `Main` — см. раздел 11.**

Полная методичка и заполненный отчёт: [`../README.md`](../README.md). Здесь только суть задания: что строим, зачем и в каком порядке.

---

## 1. Идея в трёх предложениях

1. Стресс-тест ловит гонки случайно: какой поток когда работает, решает ОС, поэтому баг может не воспроизвестись и за миллион запусков.
2. Мы забираем это решение у ОС: пишем **свой планировщик**, который пускает потоки **строго по одному** и сам выбирает, кто сделает следующий шаг.
3. Тогда любое выполнение многопоточной программы описывается строкой вроде `AABBAABB` (кто ходил на каждом шаге). Её можно **повторить** один в один, а все такие строки можно **перебрать** и найти плохую.

После этого смотрим, где такой подход **не работает**: если в коде нет точки переключения или если процессор сам переставляет операции в памяти.

---

## 2. Словарь

| Термин | Что значит |
|---|---|
| **Пауза** (точка переключения) | Место, где поток отдаёт ход планировщику: перед обращением к `Shared`, `SchedLock` и перед `await`. |
| **Решение** | На каждой паузе планировщик спрашивает стратегию, какой поток пустить. Одна пауза — одно решение. |
| **Трасса** | Буквы потоков, выбранных во всех решениях подряд: `AAAABB`. Это полный рецепт прогона. |
| **`enabled`** | Потоки, которые могут сделать шаг прямо сейчас. Не входят: завершённые, ждущие занятый лок, ждущие ложное условие `await`. |
| **Вытеснение** | Выбран другой поток, хотя прошлый (`last`) был в `enabled` и мог продолжить. Если прошлый закончил работу или заблокирован, переключение вытеснением не считается. |
| **Deadlock** | Живые потоки есть, а `enabled` пуст. Печатается как `DEADLOCK held={a:A, b:B}`. |

## 3. Как устроен планировщик

```
      ┌─────────────── главный цикл run() ───────────────┐
      │                                                  │
      ▼                                                  │
 собрать enabled ──► strategy.pick() ──► разбудить поток ──► ждать, пока он
      │                                  (его семафор)      дойдёт до паузы
      │                                                     или закончит
      └─► enabled пуст: все закончили → конец; кто-то жив → DEADLOCK
```

- У каждого потока свой `Semaphore`. В любой момент работает **ровно один** поток, остальные спят.
- Поэтому внутри `Shared` никакой синхронизации не нужно: гонок между потоками просто не бывает.
- Синхронизация внутри планировщика: только `Semaphore` (требование задания).

## 5. Правила пауз

От них зависят **все** числа в лабе.

1. **Пауза перед каждой операцией с общим состоянием**: `Shared.get/set`, `SchedLock.lock/unlock`.
2. **Без пауз подряд.** Если поток с прошлой паузы ничего общего не трогал, следующая операция выполняется без паузы.
3. **`point()`** (`window()` в тестах) сам паузу не ставит, но делает следующую паузу обязательной. В лог пишет `window`.
4. **Занятый лок.** Поток ждёт и не попадает в `enabled`, пока лок не освободится.
5. **`await(cond)`.** Пауза ставится, если поток трогал общее состояние **или** условие сейчас ложно. Пока условие ложно, поток не в `enabled`. Потом пишет `await done` и, как `point()`, требует паузу перед следующей операцией.
6. **Старт.** `run()` доводит каждый поток до паузы перед первой операцией, так что первое же действие планировщика — уже выбор.
7. **Завершение** потока возвращает ход планировщику.

Пример, `withdraw-v1` со стратегией `first`. ⏸ — пауза, трасса `AAAABB`:

```
⏸ A lock mu     ⏸ A unlock mu   A window   ⏸ A lock mu   ⏸ A unlock mu   (A закончил)
⏸ B lock mu     ⏸ B unlock mu   B window   (B закончил: баланс 0, списывать нечего)
```

## 6. Стратегии

| Стратегия | Как выбирает | Команда runner'а |
|---|---|---|
| `FirstAlive` | Всегда `enabled.get(0)` | `first` |
| `Replay(trace)` | На i-м решении поток `trace[i]`. Если такой поток не в `enabled` или трасса кончилась раньше прогона — исключение | `replay <трасса>` |
| `RandomPick(seed)` | `enabled.get(rnd.nextInt(enabled.size()))`, `rnd = new Random(seed)` | `random <seed>`, `randoms <N>` |
| `Dfs(bound)` | Перебирает все пути в дереве решений, варианты в порядке A, B, C. Каждый прогон начинается с нуля. С `bound = K` не предлагает вариантов, при которых вытеснений стало бы больше K | `dfs`, `bounded <K>` |

## 7. Тестовые программы и их баги

| Программа | Что делает | Баг |
|---|---|---|
| `withdraw-v0` | Два потока снимают по 100 с баланса 100; баланс — `Shared`, лока нет | Гонка чтение–запись → `OVERDRAFT` |
| `withdraw-v1` | Проверка и списание в **разных** критических секциях | Check-then-act: оба проверили, оба списали → `OVERDRAFT` |
| `withdraw-v2` | Проверка и списание в **одной** критической секции | Бага нет |
| `transfer` | A берёт локи `a→b`, B берёт `b→a` | Взаимная блокировка → `DEADLOCK` |
| `collector-nostep3-WxN` | Двойная буферизация из лабы 1 без повторной проверки `active` | Потеря записи → `LOST` |
| `collector-plain-1x1` | То же, но `inside` — обычный `int` | Баг есть, но DFS его **не видит**: нет точки переключения |
| `collector-acqrel-1x1` | Шаг 3 на месте, но порядок памяти release/acquire | Баг есть только на реальном железе, DFS его **не видит** |
| `collector-ok-1x1` | Корректная версия | Бага нет |

Имя коллектора: `collector-<вариант>-<писатели>x<вызовов record()>`.

## 8. Этапы: что сделать на каждом

| Этап | Пишем | Запускаем | Что понять |
|---|---|---|---|
| **0. Стресс** | — | `Stress 10000 none/yield v1`, `none v2` (по 3 раза) | Результат стресс-теста случаен; 0 ошибок не значит, что их нет |
| **1. FirstAlive** | `Scheduler`, `Shared`, `FirstAlive` | `withdraw-v0 first log` | Планировщик детерминирован |
| **2. Локи и deadlock** | `SchedLock`, проверка deadlock, `Replay` | `withdraw-v1 first log`, `transfer replay AB log` | Deadlock ловится сразу, без тайм-аутов; плохое расписание задаётся руками |
| **3. Random** | `RandomPick` | `withdraw-v1 randoms 1000` | Упавший seed даёт трассу, которая повторяется 10/10 |
| **4. DFS** | `Dfs` | `dfs` для v1, v2, v0, `transfer` | Полный перебор находит все плохие расписания (для расставленных пауз) |
| **5. Bounded** | `bound` в `Dfs` | `bounded 0/1/2` | Большинству багов хватает 1–2 вытеснений, а дерево при этом в разы меньше |
| **6. Коллектор** | — | `collector-*` через `dfs` / `bounded` | Как растёт дерево; где DFS слепнет (`plain`, `acqrel`) |
| **7. Store Buffering** | — | `MiniStress plain/acqrel/volatile/naive` | Процессор переставляет «запись → чтение»; перебор чередований этого не видит |

После каждого этапа нужно заполнить таблицу в форме отчёта и ответить на вопросы (1–2 предложения).

## 9. Самопроверка

Эти выводы должны совпасть **точно**:

```
$ ./lab2 withdraw-v0 first
schedule AAAB -> ok

$ ./lab2 withdraw-v1 first
schedule AAAABB -> ok

$ ./lab2 transfer first
schedule AAAABBBB -> ok

$ ./lab2 transfer replay AB log
  A  lock a
  A  window
  B  lock b
  B  window
schedule AB -> DEADLOCK held={a:A, b:B}

$ ./lab2 collector-ok-2x1 bounded 2
explored 1334 schedules, 0 fail  (... s)
```

Если не совпадает `1334`, значит, расходятся правила пауз для `await` или старта либо определение вытеснения.

## 10. Главный вывод лабы

| Ступень | Инструмент | Что ловит | Где слепнет |
|---|---|---|---|
| Стресс-тест | Много запусков | Баги, если повезёт | Редкие чередования, невоспроизводимость |
| **L3** (наш планировщик) | Перебор чередований | Все плохие порядки шагов, детерминированно | Нет точки переключения (`plain`); переупорядочивание памяти процессором (`acqrel`) |
| **L4** (mini-jcstress) | Реальное железо | Аппаратные эффекты: исход `(0,0)` в Store Buffering | Зависит от стенда, ничего не доказывает |

Ноль ошибок у DFS означает «ни один порядок **расставленных шагов** не ломает программу», а не «программа корректна».

## 11. Настройка и запуск (Java)

Все параметры задаются в начале [`src/lab2/Main.java`](src/lab2/Main.java)
**перед стартом**. После изменения переменных перекомпилируйте приложение и
запустите `Main` из IDE или выполните из `student-java`:

```bash
javac -d out src/lab2/*.java
./lab2
```

Аргументы командной строки больше не принимаются. Примеры CLI в разделах выше
и в исходной методичке обозначают сценарии; их параметры теперь переносятся
в переменные `Main` по таблице ниже. Форматы результатов и алгоритмы прежние.

| Переменные Main | Назначение |
|---|---|
| `EXPERIMENT` | `SCHEDULER` (этапы 1–6), `STRESS` (этап 0), `MINI_STRESS` (этап 7) |
| `TARGET` | `withdraw-v0/v1/v2`, `transfer`, `collector-<variant>-<writers>x<n>` |
| `STRATEGY` | `FIRST`, `RANDOM`, `RANDOMS`, `REPLAY`, `DFS`, `BOUNDED` |
| `LOG` | Пошаговый лог `FIRST`, `RANDOM` и `REPLAY` |
| `RANDOM_SEED`, `RANDOM_RUNS`, `REPLAY_RUNS` | Seed (начальный для `RANDOMS`), число seed'ов, проверок воспроизведения |
| `REPLAY_TRACE`, `PREEMPTION_BOUND` | Трасса `REPLAY` и предел вытеснений `BOUNDED` |
| `STRESS_RUNS`, `STRESS_WINDOW`, `STRESS_VERSION` | Число прогонов, `none/yield/sleep`, `v1/v2` |
| `MEMORY_MODE`, `MEMORY_ROUNDS`, `MEMORY_CELLS` | `plain/acqrel/volatile/naive`, раунды и размер пачки |

| Сценарий из методички | Что задать в Main |
|---|---|
| `withdraw-v1 first` | `EXPERIMENT = SCHEDULER`, `TARGET = "withdraw-v1"`, `STRATEGY = FIRST` |
| `transfer replay AB log` | `TARGET = "transfer"`, `STRATEGY = REPLAY`, `REPLAY_TRACE = "AB"`, `LOG = true` |
| `withdraw-v1 randoms 1000` | `TARGET = "withdraw-v1"`, `STRATEGY = RANDOMS`, `RANDOM_SEED = 0`, `RANDOM_RUNS = 1000`, `REPLAY_RUNS = 10` |
| `collector-ok-2x1 bounded 2` | `TARGET = "collector-ok-2x1"`, `STRATEGY = BOUNDED`, `PREEMPTION_BOUND = 2` |
| `Stress 10000 yield v1` | `EXPERIMENT = STRESS`, `STRESS_RUNS = 10000`, `STRESS_WINDOW = "yield"`, `STRESS_VERSION = "v1"` |
| `MiniStress acqrel 2000 10000` | `EXPERIMENT = MINI_STRESS`, `MEMORY_MODE = "acqrel"`, `MEMORY_ROUNDS = 2000`, `MEMORY_CELLS = 10000` |

Для значений enum используйте префикс как в исходнике: `Experiment.STRESS`,
`ScheduleStrategy.REPLAY`. В строках с `TARGET` подразумевается `EXPERIMENT = SCHEDULER`.
В режиме `naive` фактическая пачка — одна ячейка, число раундов — `MEMORY_ROUNDS * MEMORY_CELLS`.

Отдельные точки входа `java -cp out lab2.Stress` и `java -cp out lab2.MiniStress`
также работают без аргументов и используют настройки из `Main`.

Не запускайте полный `DFS` для `collector-nostep3-2x1`: это 3,7 млн расписаний,
на M4 около 9 минут. Для этой программы используйте `BOUNDED` с `PREEMPTION_BOUND` от 0 до 3.
